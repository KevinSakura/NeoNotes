## 错误原因与改法

已检查用户歌曲的最近失败任务 `57508e821b5243d385e962fc28162b9e`：模型引用键盘音符57，而其返回的主旋律只有57个音符，有效索引0–56。该任务固定键盘前缀0个、过滤0个，所以这次越界来自模型返回内容，并非程序删去音符造成。其他近期失败还包括换气不足和60秒结尾不完整；旧失败、用量和原歌曲保持原样。

旧合同要求模型分别输出主旋律音符表与逐字词编号表，还要维护相同时间轴，长歌词容易在编号、覆盖和时间上失配。新版使用 `lyric-motifs-v1`，改变生成合同与编配方法，不自动减1、猜测旧引用或把被拒规划补成成功。

- 模型按原歌词行顺序设计旋律型、句尾收束、和声、速度、曲风和四声部音色；不输出 `note_indices` 或音符ID。
- 每句旋律型包含若干字词旋律单元，单元可有1–12个音符；按明确规则顺序循环，最后一个字词使用句尾收束。短句可设计较完整的单元序列，长句也可以使用循环旋律型。这不是人声或中文语音处理。
- 程序使用已经分好的原中文字符/英文词，逐词展开，同时建立实际音符与对应，不让模型再维护第二份全局编号表。
- 程序按共同4/4小节与和声安排前奏、间奏、尾奏及鼓/吉他/贝斯；句间留至少1拍并对齐小节。最末实际音符形成结尾，不用静音补足失败结果。
- 伴奏采用明确的基础节奏型，支持稀疏、稳定和较密三种；必要时减伴奏密度以满足5000音符边界，仍保留全部歌词和主旋律。编配的重复是否自然、伴奏是否丰富需人工评估。
- 保留模式将原演奏原样作为无词前缀，歌词在窗口之后开始。音高、秒级时间、力度和Program/Bank约束继续有效；原键盘前缀仍须单旋律。自由改编继续将原走向提供给模型，是否合理延展需要人工对照。

## 当前范围与使用

1. 停止旧服务，双击根目录 `启动工作台.cmd`，在Chrome/Edge打开 `http://127.0.0.1:8000`。Python仍统一使用 `conda run -n piano`，没有新增依赖。
2. 上传UTF-8 TXT或粘贴歌词，自动使用框内全部非空行，页面显示64行/1024字词边界；不再勾选60秒选段。只有标点的行需去除，超限不自动裁词。
3. 填主题与音乐感觉，点击“AI生成全文歌词候选”。真实模式确认发送全文及使用额度；启动和状态检查不调用模型。每个任务只请求一次。
4. 时长按全文、旋律型、换气和器乐段实际编配，可少于或超过60秒；仍限10分钟/5000音符。字词上限不保证任何速度、花腔或曲风都能放进这两个边界。
5. 试听、逐句试唱，再明确“采用到编辑器”。采用保存新版本，审核需亲自确认，修改另存后重新审核；不会自动通过或再发请求。
6. 全文歌词作品可直接整体修改、手动编辑和导出，无需再次走短曲→全文步骤。歌词修改保留全文，时长可以随新乐句改变；无歌词短曲和整曲修改仍保持既有时长规则。
7. “本次不使用歌词”保留文字和原文件，但本次只发送主题/感觉/演奏；“使用歌词全文”可恢复。没有歌词的60秒短曲→人工审核→明确195秒整曲继续保留。

旧歌曲、旧候选、旧审核来源与编号诊断按旧合同读取，不做文件迁移或失败重分类。正常歌曲仍在 `data/<歌曲ID>/`，原型仍在 `frontend/prototype/`。本次真实复验只采用到隔离目录，不写正式歌曲，也不冒充人工音乐批准。

`.env.example`只更新无密钥说明；既有配置和SoundFont无需重建。全文谱曲/修改及整曲单次32768输出token，即使旧配置为12000也生效；无歌词60秒任务仍尊重配置值。配置仍仅由后端加载器读取，助手没有打开、展示或修改真实 `.env`。
