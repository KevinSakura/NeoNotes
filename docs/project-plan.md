## 定位与已确认边界

面向零基础新手的本地编曲助手：通过模拟电子琴探索旋律，结合主题与情感描述，由 AI 生成可编辑、可播放和可导出的作品。

- 平台在本地运行与访问，允许联网调用 AI API。
- 用户通过电脑键盘触发虚拟琴键和音色，录入演奏片段。
- 片段主要承担灵感和旋律约束作用；支持保留或自由改编。自由改编按初始旋律走向向后延展，不是任意重写；也支持跳过演奏、直接用文字生成。
- 第一版支持上传歌词 `.txt` 并选择其中一段，为所选歌词生成能照词演唱的旋律与伴奏，不要求先输入演奏片段。首版以器乐试听，不合成人声。
- 初始声部为键盘、鼓、吉他、贝斯，电子琴通过按钮切换音色。
- 先生成 60 秒短曲，经人工审核满意后才进入全曲生成；不得自动推进下一阶段。
- 支持 MIDI 读取、编辑、自动演奏和导出，并通过音色渲染后导出 MP3。
- AI 编曲按乐器声部组织生成后统一组合，导出 MIDI 保留可区分的轨道及实际乐器信息。该要求同时适用于首版短曲和后续长曲。
- 首版包含手动及自然语言修改。手动支持音符增删、移动、时长调整，以及声部切换、音色、音量、独奏、静音和撤销；自然语言局部修改、单声部重生成留待后续。
- 每首歌在平台中新建独立工作目录，如 data/a、data/b，分别保存输入、生成的 MIDI、MP3、修改历史等工作记录。
- 同时提供多种输入时，歌词描述优先，其次情感描述，旋律走向在前两者约束下参考；歌词表达内容与期望曲风分别处理，允许悲伤歌词搭配积极向上的音乐。
- 优先形成初步可用的平台，保留后续扩展空间；不提前实现人声和长曲功能。
- 当前保留独立 HTML 交互原型，正式第一、第二阶段已分别获授权。见 [第一阶段交付](stage1.md)、[第二阶段交付](stage2.md)、[技术栈与项目架构](technical-stack.md)、[原型说明](prototype.md)。原型采用明确标示的示例数据；模型编曲能力仍待验证，真实调用需单独授权。

## 建议的内部结构

前端负责演奏、编辑和试听；后端负责 AI API 调用、音乐数据检查、工程文件管理和音频导出。Python 工作统一在 Conda 的 piano 环境中进行。

建议使用统一的音乐数据表示，包含速度、轨道、乐器和音符事件。手动录入、MIDI 导入和 AI 生成都转换到这一表示，再供编辑、播放和导出使用。

生成模型通过独立的适配模块接入。平台检查返回内容能否构成合法的音符和轨道，但格式正确不等于音乐好听；还需试听评估情绪表达、段落连贯性和输入旋律的利用情况。

旋律自由改编已明确为依据初始旋律走向向后延展；实现时可分析上行／下行、重复和乐句发展，并将其作为续写约束。这些分析方式是建议，不代表已确定算法。保留模式对音高、节奏及片段位置的精确规则仍待细化，不预设数值化的自由度滑块。

歌词谱曲是一条独立创作入口：上传 TXT → 读取并选择一段歌词 → 理解歌词内容与期望曲风 → 规划可照词演唱的旋律与配器 → 生成 60 秒 MIDI → 器乐试听、人工试唱审核及导出。保留歌词原文、选择范围和歌词与旋律的对应关系，不能只提取情绪关键词后丢弃词句约束。

可唱性已是首版要求，具体歌词—音符对齐格式、显示方式仍待设计，不等同于已经要求卡拉 OK 字幕。长歌词由用户选择一段用于短曲；若选段无法合理适配 60 秒，建议提示用户调整选择，不静默删词或塞入不合理的节奏。

输入优先级需按作用分别落实：歌词决定所唱的文字和表达内容，情感描述规定期望的音乐风格与情绪处理，旋律提供走向和延展依据。“悲伤歌词＋积极曲风”是有效要求，不能自动改成悲伤曲风。若保留旋律与歌词可唱性发生实质冲突，建议提示冲突，不默默宣称两者都已满足。

工程按歌曲隔离保存：data/a 存放歌曲 a 的工作记录，data/b 存放歌曲 b 的工作记录，支持重新打开继续编辑。目录内部建议分别组织输入、工程状态、导出文件和修改历史；具体文件名未定，也不因此创建示例歌曲目录。自然语言修改应保存指令及对应结果，人工审核记录建议关联具体版本，避免误将旧版本的认可用于新版本。

对 API 超时或无效输出，建议保留用户输入和已有作品，显示失败原因，并由用户选择重试，不让失败覆盖原作品。

## 分声部生成与文件约定

首版短曲和后续长曲均按声部组织。前文 A／B 按上下文分别理解为短曲阶段和后续长曲阶段；长曲依然要在短曲效果满意后再推进。

建议流程：

1. 根据主题、情感、歌词或用户演奏，形成共同的速度、拍号、调性／和声、段落长度和配器规划。
2. 在规划下组织键盘、鼓、吉他、贝斯四个初始声部，安排主旋律、和声伴奏、低音和节奏功能。具体进入和休止位置由编曲决定，不要求四个声部全程同时发声。
3. 生成后续声部时参考已有声部与输入约束，检查段落对齐、和声配合、音域和结尾，允许必要的整体修订。鼓声部主要是节奏事件，不要求每个声部都是独立旋律。
4. 保持声部独立可识别，将其组合到同一时间轴，供整曲播放、编辑和导出。

分声部是数据和编曲组织要求，不规定每个声部必须单独调用一次 API，也不要求并行生成；实际模型可以一次返回多声部，或由平台分步调用工具构建。

MIDI 导出约定：保留各声部的音符和时间信息、轨道名称、正确的通道分配及乐器选择信息；鼓声部使用与约定播放标准一致的打击乐映射。名称不能替代实际乐器设置。工程内可另存“主旋律”“伴奏”等角色，不能假设外部播放器会理解这些创作角色。

自产 MIDI 需验证导出后重新导入仍能区分声部并读取乐器信息，避免不同乐器误用同一通道导致音色互相覆盖。同一种乐器的不同声部仍可保持独立，不强制合并。任意外部 MIDI 可能缺少这些信息，不据此承诺全部可自动准确分类。

首版需利用这一结构支持声部选择、独奏、静音、音色与音量调整，并通过按钮切换电子琴音色。MP3 是各声部合成后的音频，不能代替 MIDI 或工程数据保存可编辑声部。

## 建议的首版验收流程

1. 新手能够通过操作提示完成试弹、录制和回放，也能直接进入文字生成。
2. 输入主题与情感；有旋律片段时，可选择保留或自由改编。
3. 得到 60 秒短曲，含键盘、鼓、吉他、贝斯声部，并确认歌词、情感、旋律约束按优先级处理。验收细则需明确音乐结束点、渲染尾音的计时及误差容限，不能擅自把 60 秒放宽成时长范围。
4. 对生成或导入的 MIDI 验证已确认的手动编辑操作、试听及撤销；对生成作品验证自然语言整曲修改、对应历史记录及撤销，局部修改与单声部重生成不列入首版验收。
5. MIDI 导出后可重新导入；MP3 导出后能够播放。
6. 人工审核短曲的旋律、段落、声部配合及情感表达，只有人工明确认可后才推进全曲生成；不以“文件有效”替代人工审核，不自动启动全曲阶段。
7. 独立验证歌词入口：正确读取 TXT 并选择一段，在不提供演奏片段时也能生成 MIDI；人工照着所选歌词试唱，检查词句与旋律能否配合、停顿是否自然，以及歌词内容与期望曲风是否兼顾。无需合成人声。
8. 检查 AI 生成结果的声部与乐器信息：导出并重新导入 MIDI 后，各声部仍可区分、音符时序不丢失、乐器选择可读取且鼓声部正确解释；整曲试听时各声部按共同规划配合。
9. 在平台创建歌曲 a 和 b，核对 data/a、data/b 中各自的 MIDI、MP3 和修改历史；切换或重新打开工程后内容正确恢复，两个歌曲的工作记录不混用。

以上是依据已确认范围整理的验收流程建议，不是已通过的测试。人工审核是已确认的阶段门槛，具体评审记录格式、模型效果、等待时间和调用成本仍需后续设计或评估。
